# «دیتابیس قوی» — یک لایهٔ محکم روی همان دیتابیس دوم

**درخواست:** «فقط یه کاری بکن که دیتابیس قوی داشته باشیم».

**یک کار کردم، نه یک مسیر تازه:** بهجای اضافه کردن حامل/سرویس/تحقیق
دیگر، همان چیزی که داری (Internet Archive + پیامهای ذخیرهشدهٔ روبیکا +
نسخهٔ محلی) را به یک **دیتابیس دوم ضدخرابی، تکثیرشده، قابلتأیید و
خودترمیم** تبدیل کردم. ماژول تازه:
[`r2-relay/strong-db/`](../r2-relay/strong-db/README.md).

**وضعیت:** Supabase همچنان دیتابیس اصلی است و **دستنخورده** مانده. مقصد دوم
همچنان Internet Archive است (انتخاب قبلی صاحب پروژه). مسیر `maxrubika`،
کدبوک واژگان و تحقیق TeraBox سر جای خود هستند. صفر حذف/ریست، بدون ورسل،
بدون استقرار، بدون مرج، بدون حساب/کلید/لاگین تازه.

## ۱. «قوی» یعنی چی؟ (چهار ضمانت قابلاندازهگیری)

| # | ضمانت | چطور پیاده شد | چطور تست شد |
|---|---|---|---|
| ۱ | **تمامیت رمزی** | همان بستهٔ `MCIA1` با **ChaCha20-Poly1305**، `AAD = item\|filename\|batchId`، و SHA-256 هم متن و هم ciphertext. کلید همان کلید داخل سورس (`key.mjs`) است. | دستکاری یک بایت blob → `get` رد میشود، ولی هیچچیز پاک نمیشود |
| ۲ | **تکثیر + تأیید نوشتن** | هر blob روی **۳ حامل مستقل** نوشته میشود: `internet-archive` (همان رابط IAS3)، `saved-messages` (همان متنهای `MCR1/MCPK1`)، `local` (نسخهٔ محلی سمت primary). بعد از **هر** نوشتن، همان blob خوانده و هش آن مقایسه میشود؛ اگر حتی یکی تأیید نشد رکورد ثبت **نمیشود** (و هیچی پاک نمیشود). | `put` → `replicas.every(ok===true)`؛ شکست عمدی → `STRONG_DB_REPLICA_VERIFY_FAILED` |
| ۳ | **کاتالوگ ضددستکاری** | فایل JSONL **فقطالحاقی** `MCDB1`؛ هر رکورد `seq` + `prevHash` + `hash = SHA-256(prevHash + canonical-JSON)` دارد. تغییر یا برداشتن رکورد قدیمی زنجیر را میشکند. | دستکاری رکورد ۱ → `chainOk:false`، `brokenAt:0`، تعداد رکوردها ثابت |
| ۴ | **خودترمیمی** | اگر یک نسخه خراب/ناپدید شد، `get` از نسخهٔ سالم بعدی میخواند و یک رکورد `repair` الحاق میکند. نسخهٔ خراب **پاک نمیشود**؛ فقط علامت میخورد. در `trial`، برای نشان دادن سلامت دوباره، همان بستهٔ تأییدشده در همان جای **fixture** نوشته میشود (هیچ رکورد کاتالوگ یا ردیف Supabaseـای عوض نمیشود). | خرابکردن نسخهٔ IA → برگشت موبرهمو از `saved-messages`، `repaired:true` |

اضافه بر اینها: `verifyAll()` کل زنجیر، کل رکوردها و **تکتک نسخهها** را
دوباره میخواند، هش میگیرد و رمزگشایی میکند و گزارش سلامت میدهد.
`status()` وضعیت را صادقانه میگوید.

## ۲. معماری (همهچیز اضافهای، هیچچیز جابهجا نشد)

```
Supabase  = دیتابیس اصلی (بدون تغییر)
   │
   └── StrongDb (لایهٔ محکم)
         │  MCIA1 = ChaCha20-Poly1305(plain, AAD=item|filename|batchId)
         │  sha = SHA-256(MCIA1)
         ├──► internet-archive   : همان ترانسپورت IAS3 (آفلاین: FixtureIas3)
         ├──► saved-messages     : همان MCR1.MCPK1... (آفلاین: همان کدک maxrubika)
         └──► local              : نسخهٔ محلی، همیشه نگه داشته میشود
         │
         └──► catalog.jsonl      : MCDB1 فقطالحاقی + زنجیر هش
              replicas.json      : ماندگاری سه نسخه (همه gitignored)
```

هیچ API، endpoint، سرویس یا کتابخانهای اختراع نشد: `encryptEnvelope` /
`decryptEnvelope` از `internet-archive/cipher.mjs`، `makePackets` /
`joinPackets` و کدک `MCR1` از مسیرهای قبلی، و `FixtureIas3` مستقیماً
دوباره استفاده شدند.

## ۳. صداقت (مهمتر از کد)

| موضوع | واقعیت |
|---|---|
| **محرمانگی** | ❌ ادعا **نمیشود**. مخزن GitHub عمومی است و آیتمهای IA «World readable»اند؛ کلید داخل سورس برای همه قابلدیدن است. این لایه فقط **تمامیت + افزونگی** میدهد. همان محدودیتی که در `docs/SECOND-DB-INTERNET-ARCHIVE.md` گفته شد پابرجاست. |
| **کوئریپذیری** | ❌ **دیتابیس کوئریپذیر نیست**: SQL، تراکنش، ایندکس، OTP و realtime ندارد. دیتابیس اصلی کماکان Supabase است. «قوی» اینجا یعنی ضدخرابی و قابل بازیابی، نه جایگزین Postgres. |
| **اجرای واقعی** | ❌ تمام حاملها **آفلاین/fixture**اند: هیچ آپلود IAS3، هیچ لاگین/سشن/ارسال روبیکا، هیچ شماره/OTP/توکن، هیچ استقرار، مرج، ورسل یا بکاند عمومی. |
| **حذف** | ✅ صفر. `delete()` عمداً `STRONG_DB_NO_DELETE` میدهد؛ هیچ `DELETE`/`DROP`/`TRUNCATE`/`RESET`ـای صدا زده نمیشود. رکورد `repair` و `replica-restored` الحاق میشوند، نه جایگزینی مخرب. |
| **دادهها** | ✅ ساختار، نام جدولها، فیلدها و ردیفها دستنخورده؛ نسخهٔ محلی هر بسته هنگام `put` نگه داشته میشود (`retainedInPrimary: true`). |

اگر «قوی» بهمعنای **واقعی** (دیتابیس SQL خصوصی + محرمانگی) باشد، آن نیاز به
سرویس و کلید بیرون از مخزن دارد و بدون اجازه/اعتبار انجام نشد — الکی هم
ادعا نمیکنم.

| فایل | کار |
|---|---|
| `r2-relay/strong-db/catalog.mjs` | `Catalog` فقطالحاقی `MCDB1` + زنجیر SHA-256 + `verifyChain` / `index` |

هیچ blob یا کاتالوگی وارد مخزن نشد.

## ۵. خروجی واقعی `trial` (همینجا اجرا شد)

```text
زنجیر کاتالوگ هنگام شروع: سالم | رکوردهای قبلی: 0
نوشتهها: 3 | نسخهها برای هر رکورد: 3 | الگوریتم: ChaCha20-Poly1305
تأیید نوشتن (write-verify): true
برگشت موبرهمو: true | سلامت اولیه: true | نسخههای چکشده: 9
بعد از خرابکردن یک نسخه: سلامت=false | خراب=1 | خودترمیمی از «saved-messages»: true
بعد از ترمیم: سلامت=true | خراب=0 | رکورد repair: 1
حذف/ریست: false | عملیات مخرب: 0 | Supabase: بدون تغییر | دیپلوی/مرج/ورسل: خیر
⚠️ تمامیت و افزونگی بله؛ محرمانگی خیر (مخزن public + آیتمهای IA عمومی). کوئریپذیر هم نیست.
```

یعنی: سه رکورد نوشته شد، نه نسخه بررسی شد، یکی عمداً خراب شد → سیستم
فهمید، از نسخهٔ سالم خواند، ترمیم کرد و دوباره سلامت کامل گرفت. هیچ چیزی
پاک نشد.

## ۶. تستها

```text
npm --prefix r2-relay run test:all
  13 (پایه) + 7 (rubika) + 16 (maxrubika) + 22 (IA) + 19 (TeraBox)
  + 16 (strong-db) = 93 تست JS سبز
python3 -m unittest discover -s r2-relay/maxrubika/tests -p "test_*.py"
  14 تست Python سبز
```

تستهای `strong-db` شامل: زنجیر هش و شکستن آن، ماندگاری کاتالوگ/نسخهها
بین دو نمونه، write-verify روی ۳ حامل، برگشت موبرهمو+AAD+Poly1305،
شناسهٔ تکراری، `delete` ممنوع، خودترمیمی، رد بستهٔ دستکاریشده،
شکست نوشتن (رکورد `write-failed` الحاق میشود ولی `put` ثبت نمیشود)،
رزرو بودن فیلدهای سربرگ کاتالوگ، و `status` صادقانه (بدون ادعای
محرمانگی/کوئریپذیری).
