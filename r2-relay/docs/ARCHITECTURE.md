# معماری پیشنهادی: R2 بهعنوان واسطه، بدون Supabase (طرح، اجرا نشده)

> **بهروزرسانی تصمیم:** بنا به اعلام صاحب پروژه، گپ و روبیکا ساخته نمیشوند. سطرهای مربوط
> به «روبیکا / کوریر دستی / آینهٔ پیامرسان» در ادامه **سابقهٔ طرح قبلی**اند و از برنامهٔ
> فعال خارج شدهاند. طرح فعال از R2 / Drive / GitHub / GitLab / کش دستگاه استفاده میکند.
> هیچ کدی حذف یا تغییر نکرده است.


## اصل ثابت
نشانی کاربران تغییر نمیکند: `https://zahradavoodi69-code.github.io/memechat/`.
هر تغییری فقط در `origin`ـه API/بلابها است، آنهم در پسزمینه.

## ۱. تقسیم واقعی کار

| لایه | چه میکند | چه نمیکند |
|---|---|---|
| GitHub Pages (همان URL) | `index.html` ایستا | اجرای کد سرور، نشست، DB |
| **Cloudflare Workers** | تنها محاسبه: احراز HMAC، CORS، manifest، verify/commit، مسیردهی | ذخیرهٔ حجیم (→ R2) |
| **R2** | بلاب ciphertext + manifest کوچک + کش داغ؛ **egress = ۰** | کوئری، تراکنش، auth |
| D1 / Durable Objects / KV | ایندکس، شمارنده، هماهنگی، سیگنالینگ WebRTC | جایگزینی مستقیم Postgres بدون بازنویسی |
| Google Drive / GitHub / هاست فایل / روبیکا | **آینهٔ سرد** (mirrors) | سرور، CPU، SLA، CORS تضمینی |
| کلاینت (مرورگر / WebView) | رمزگذاری/رمزگشایی، تأیید SHA، کش | نگهداری توکن ارائهدهنده |

پس جملهٔ «خودشون سرور بشن و پردازش کنن» از نظر فنی این میشود: **کد پردازش روی
Workers اجرا میشود و همان کد است که به آن سایتها مینویسد/از آنها میخواند.** خود
سایتها فقط دیسکاند. GitHub Actions هم فقط برای کارهای دستهای/آفلاین مناسب است
(نه poll زندهٔ ۳٫۵ ثانیهای).

## ۲. جریان داده

```
کلاینت: plaintext ──AES-256-GCM──▶ chunks(ciphertext)
        │
        ├─▶ [primary] Worker /v1/blob  ──▶ R2: stage/<batch>/<i>
        ├─▶ [mirrors] Drive / GitHub / file host / Rubika(courier)  ← فقط ciphertext
        │
Worker /v1/sync/verify : SHA-256 تککتک بچها را میخواند (بدون حذف)
Worker /v1/sync/commit : تأیید همه ▶ ارتقا به blob/<sha> ▶ حذف stage/*
        │
manifest کوچک در R2: { id, sha, chunks:[{sha,iv,size,provider}], commit, status }
        │
کلاینت: GET /v1/blob/<sha> (immutable, ETag, cache) ──▶ رمزگشایی ──▶ میم چت
```
قانون «اول تأیید، بعد حذف» دقیقاً همان `api/sync.js` است، فقط واسطه از Supabase به R2
منتقل شده. `status: confirmed` + `commit` جای `github_commit_sha` را میگیرد.

## ۳. چرا R2 «خیلی کم» شدنی است
manifest و ایندکس چند کیلوبایتاند؛ بلابها محتواآدرسپذیر (`blob/<sha>`) و immutableاند
(یکبار مینویسیم، هزاربار میخوانیم). ولی دو نکتهٔ صادقانه:
- اگر Worker بلابهای سردِ آینهها را برای تحویل به R2 کپی کند، حجم R2 دیگر «خیلی کم»
  نمیماند؛ یا باید کلاینت مستقیم از آینه بگیرد (CORS/ToS/دوام → مسئلهدار) یا R2 کش کند.
- `r2.dev` برای تولید نیست (rate-limited، بدون کش لبه). تولید = custom domain + CORS policy.

## ۴. حساب سهمیهها (اعداد واقعی، نه تبلیغی)

| منبع | سقف رایگان | اثر روی میم چت |
|---|---|---|
| R2 storage | ۱۰ GB-month | ≈۵٬۶۸۹ پیام ۱٫۸MB (بدون فشردهسازی) |
| R2 Class A | ۱M/ماه (≈۳۳هزار/روز) | نوشتن بهازای پیام/بچ، خیلی زود تمام نمیشود |
| R2 Class B | ۱۰M/ماه (≈۳۳۳هزار/روز) | خواندن بلاب؛ با `immutable` مرورگر کش میکند |
| R2 egress | **۰، بدون شرط** | همان چیزی که ایمیل ۶ دسامبر Supabase را حل میکند |
| Workers Free | ۱۰۰هزار req/روز، ۱۰ms CPU/req، ۵۰ subreq، ۱۲۸MB | ≈۴ کلاینت دائم با poll ۳٫۵s ← **گلوگاه اصلی** |
| KV Free | ۱۰۰هزار خواندن / ۱۰۰۰ نوشتن در روز | شمارندهٔ rate limit را نباید روی KV گذاشت |
| Pages | سقف نرم ۱۰۰GB/ماه، سایت ≤1GB | با رفتن بلابها به R2، Pages تقریباً فقط HTML میدهد |

محاسبهٔ گلوگاه: `3600/3.5 ≈ 1029` درخواست/ساعت بهازای کلاینت؛
`100000/24/1029 ≈ 4.05` کلاینت همیشهروشن. پس قبل از هر مهاجرت: **poll افزایشی +
ETag + WebSocket/Durable Objects + ادغام بچها**، وگرنه صرفاً جای ۴۰۳ را با ۱۰۲۷ عوض میکنیم.

## ۵. تأمینکنندهها، صادقانه

| تأمینکننده | نقش واقعی | گیر |
|---|---|---|
| R2 | واسطه/کش داغ/منیفست | ۱۰GB رایگان، نیاز به فعالسازی R2 در داشبورد، `r2.dev` تولیدی نیست |
| Google Drive | آینهٔ سرد شخصی | OAuth/توکن سرویس → **نباید توی مرورگر**؛ سهمیهٔ مشترک، CORS، ToS، کندی |
| هاستهای فایل «APIدار» | آینهٔ فرّار | خیلیهاشان بعد از چند ساعت/روز پاک میکنند، SLA/دوام ندارند، CORS/hotlink ممنوع |
| روبیکا | کانال حمل | Bot API رسمی v3 هست؛ اگر ربات کار نکرد → **کوریر دستی** (`MCPK1`) نه scraping |
| GitHub | آرشیو رمزشده + انتشار | Pages استاتیک؛ REST ۵۰۰۰/h، فایل >۱۰۰MiB بلاک، «Git ابزار بکاپ نیست» |

اصل امنیتی: **هیچ توکن ارائهدهندهای توی کلاینت نباشد.** هر آینهای که CORS/توکن میخواهد
از طریق Worker پروکسی میشود؛ واسطهگری دوباره توی Cloudflare است، نه Supabase.

## ۶. مهاجرت «دیگه روی سوپا بیس نباشه» — دو فاز، نه یک حرکت

**فاز A (کمخطر، توصیهٔ اول):** فقط مدیا/بچهای آرشیو از `poll` بیرون بروند و به R2 برسند؛
Supabase همچنان ورود/نشست/چت/نقشها را نگه میدارد. اثر فوری بر egress، بدون بازنویسی API.
تغییرات لازم: بیرون آوردن base64 تا ~۱٫۸MB و آواتار inline تا ۴۵KB از پاسخ `poll`،
افزودن originـه Worker به CSP، بررسی هش HTML زنده، `AppConfig` اندروید، تست رگرسیون.

**فاز B (بازنویسی کامل):** انتقال `api/auth.js` + `api/chat.js` (~۱۰۰ اکشن)، توکن HMAC،
OTP، rate limit، نقشهای `user/admin/super/owner`، `rt-post`/`rt-get` تماس و جداول
Postgres به Workers + D1/DO. `edge/entry.js` و `dist.cjs` فعلی فقط سه مسیر
`auth/chat/health` دارند؛ `/api/sync` توی باندل مستقر نیست (فقط سورس). بدون تست و
راستیآزمایی جداگانهٔ محتوای زنده، هیچچیز «تمامشده» اعلام نشود.

## ۷. خطراتی که باید قبل از فاز A تصمیمگیری شود
- نشست و احراز: `MC_AUTH_SECRET` فقط `wrangler secret put`؛ هرگز توی کد/چت/لاگ.
- بلابها ciphertextاند ولی **متادیتا لو میرود**: اندازه، زمان، تعداد، طرفین. مسیرها
  باید غیرقابل حدس باشند ≠ امنیت کامل.
- `AES-256-GCM` داخل Worker روی بچهای بزرگ، ۱۰ms CPU رایگان را مصرف میکند؛ تأیید
  سنگین را ببرید سمت کلاینت یا بچهای کوچک.
- حذف دادهٔ کاربر، ارسال پیام آزمایشی به کاربر واقعی، و جابهجایی URL کاربرها: ممنوع
  مگر دستور صریح.
- `SQL`های موجود طرح/مایگریشناند، **بکاپ زنده نیستند**.
